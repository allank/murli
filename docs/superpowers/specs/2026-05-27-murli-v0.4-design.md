# murli v0.4 — Safe Mutation and Async: Design Spec

**Date:** 2026-05-27  
**Status:** Approved  
**Milestone:** v0.4 — Safe Mutation and Async

---

## Goal

Add infrastructure for state-changing operations: dry-run support, force/yes bypass of the non-interactive mutation guard, automatic context cancellation mapping to structured errors, and a SafetyMetadata block in schema/describe output.

---

## Architecture

No new packages. All new types live in the `murli` core package; adapter wiring lands in `cobra/`, `cli/v2/`, `cli/v3/`. The four features are independent — each can be read and implemented in isolation.

## Feature 1: Dry-Run Support

### Opt-in

Engineer sets `DryRunnable: true` in `Annotate()`. Murli auto-registers `--dry-run` only on those commands. Commands without `DryRunnable` do not get the flag — no misleading signals to agents.

```go
murliCobra.Annotate(deleteCmd, murli.Metadata{
    Mutating:    true,
    Destructive: true,
    DryRunnable: true,
})
```

### Writer methods

`IsDryRun() bool` — reads the `--dry-run` flag value from the command. Engineers check this at the start of their action and return early with `WritePlan()` if true.

`WritePlan(humanText string, plan any)` — outputs a plan envelope:
- **Agent mode:** `{"status": "plan", "result": <plan>, "schema_version": "0.2"}` — same stamps as `WriteSuccess`, `"status"` is `"plan"` instead of `"ok"`. Routing respects `--output` format (json/ndjson/yaml/text).
- **TTY mode:** prints `humanText` to stdout, same as `WriteSuccess`.

### No enforcement

If the engineer does not check `IsDryRun()`, the command runs normally. The contract is: declaring `DryRunnable: true` signals to agents that `--dry-run` produces a plan rather than executing. Honouring that signal is the engineer's responsibility.

### Schema/describe output

Commands with `DryRunnable: true` surface `"dry_run_supported": true` in their `SafetyBlock` (see Feature 4). `--dry-run` is excluded from the flags list (infrastructure flag, like `--schema`/`--agent`/`--output`).

## Feature 2: --force / --yes Bypass

### Registration

`--force` and `--yes` are auto-registered as separate boolean flags on every command marked `Mutating: true`. Either one being `true` sets `Writer.force = true` (the field reserved in v0.3).

### Guard bypass

The `confirmation_required` mutation guard gains one check: if `w.IsForced()`, skip the rejection and proceed to the action. The error suggestion is updated from "wait for --force support in a future release" to "Pass --force or --yes to proceed without a TTY."

### Writer method

`IsForced() bool` — available for engineers who need to suppress their own confirmation prompts in TTY mode or adjust behaviour when forced. Not required to activate the guard bypass — that is automatic.

### Schema/describe output

`--force` and `--yes` are excluded from the flags list (infrastructure flags). Agents infer force support from `safety.read_only: false` — if a command is not read-only, force/yes are available to bypass the guard.

### Scope

`--force`/`--yes` only affect the non-interactive mutation guard. They do not change output format, do not activate agent mode, and have no effect on non-mutating commands.

## Feature 3: Context Cancellation → Structured Error

### Behaviour

All three adapters extend their existing error-wrapping path. Before the generic fallback, two new checks run using `errors.Is`:

```
returned error
  → errors.Is(context.Canceled)         → ExitCancelled (9), error_type: "cancelled",  recoverable: false
  → errors.Is(context.DeadlineExceeded) → ExitTimeout   (4), error_type: "timeout",    recoverable: true
  → anything else                       → existing behaviour unchanged
```

A timeout is recoverable — the operation may succeed if retried later. A cancellation is not — the user or system explicitly stopped it.

### No new API surface

Engineers write standard Go. Return `ctx.Err()`, `context.Canceled`, or any error that wraps either via `fmt.Errorf("...: %w", err)`. The adapter detects it automatically and emits the correct structured envelope.

### Signal handling

Murli does not register signal handlers. Engineers manage their own signals, contexts, and shutdown logic. Murli only observes what the action returns.

### TTY mode

No change — errors surface as plain text on stderr, same as today.

## Feature 4: SafetyMetadata Block

### New Metadata fields

Added flat to `Metadata`, consistent with the existing `Mutating`/`Idempotent` pattern:

| Field | Type | Meaning |
|---|---|---|
| `DryRunnable` | `bool` | Command supports `--dry-run` (see Feature 1) |
| `Destructive` | `bool` | Operation cannot be undone (delete, overwrite, truncate) |
| `Reversible` | `bool` | Operation can be undone if something goes wrong (e.g. creates a backup first) |

`ReadOnly` and `Idempotent` are already in `Metadata`. `ReadOnly` is derived as `!Mutating` at assembly time.

### SafetyBlock struct (schema.go)

```go
// SafetyBlock summarises the safety properties of a command for agent consumption.
// Assembled from Metadata fields by the adapter at schema/describe emit time.
type SafetyBlock struct {
    ReadOnly    bool `json:"read_only"`
    Idempotent  bool `json:"idempotent"`
    Destructive bool `json:"destructive,omitempty"`
    Reversible  bool `json:"reversible,omitempty"`
    DryRunnable bool `json:"dry_run_supported,omitempty"`
}
```

### Integration

`CommandSchema` (`--schema` output) and `DescribeCommandSchema` (`describe` output) both gain:

```go
Safety SafetyBlock `json:"safety"`
```

Always present. `ReadOnly = !Mutating` means the block always carries meaningful signal — even a simple read-only command tells agents it is safe to call without confirmation. Individual fields use `omitempty` only where zero means "not applicable" (`Destructive`, `Reversible`, `DryRunnable`).

### Agent value

An agent reading `describe` output can reason about risk before invoking:
- `destructive: true, reversible: false` → require explicit confirmation or `--force`
- `dry_run_supported: true` → probe with `--dry-run` first
- `read_only: true` → safe to call without confirmation

## Testing Strategy

### Core package (`murli_test.go`)
- `WritePlan` outputs `"status": "plan"` in agent mode; outputs `humanText` in TTY mode
- `WritePlan` respects `--output` routing (json/ndjson/yaml/text)
- `IsDryRun()` returns true when `--dry-run` flag set
- `IsForced()` returns true when `--force` or `--yes` set
- Context cancellation: `context.Canceled` → `ExitCancelled`; `context.DeadlineExceeded` → `ExitTimeout`
- Wrapped errors (`fmt.Errorf("...: %w", context.Canceled)`) detected correctly

### Adapter tests (all three)
- `--dry-run` registered only on `DryRunnable: true` commands, not others
- `--force` and `--yes` registered only on `Mutating: true` commands
- Mutation guard bypassed when `--force` or `--yes` present
- `SafetyBlock` present and correct in `--schema` output
- `SafetyBlock` present and correct in `describe` output
- `--force`, `--yes`, `--dry-run` absent from flags list in schema output
- `safety.read_only: false` on mutating commands in schema (implies force/yes available)

---

## Breaking Changes

None. All new fields in `Metadata` are zero-valued by default. All new flags are additive. `SafetyBlock` is `omitempty`. Existing code compiles and behaves identically.

---

## What is explicitly out of scope

- `RiskTier` (deferred — can be inferred by agents from `SafetyBlock` booleans)
- Signal handler registration (engineer's responsibility)
- Enforcement of dry-run contract (guide, not enforce)
- `--force` on non-mutating commands
